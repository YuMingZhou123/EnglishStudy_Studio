# 产品从 0 到 MVP 落地开发流程

版本：v0.1  
日期：2026-05-27  
用途：新项目启动与 MVP 落地流程模板

## 1. 流程目标

本文档用于规范一个产品从想法到可运行 MVP 的完整流程，避免每次新项目都从零讨论。适合个人开发者、AI 辅助开发、轻量团队协作场景。

核心原则：

- 先验证产品价值，再扩展功能。
- 先锁定 MVP 范围，再进入开发。
- 先跑通核心链路，再做体验优化。
- 先本地可运行，再考虑上线部署。
- 每个阶段都产出可检查的文档或代码。

## 2. 总体阶段

```text
想法澄清
↓
轻量调研
↓
产品方案
↓
功能规格
↓
技术架构
↓
开发计划
↓
MVP 范围确认
↓
页面原型
↓
工程骨架
↓
核心链路开发
↓
内测验证
↓
迭代与商业化
```

## 3. 阶段一：想法澄清

### 3.1 目标

把模糊想法变成可以讨论的产品方向。

### 3.2 需要回答的问题

- 这个产品解决什么问题？
- 谁最需要这个产品？
- 用户现在怎么解决这个问题？
- 这个产品的核心价值是什么？
- 第一版最值得验证的功能是什么？

### 3.3 产出物

- 一句话产品定位。
- 目标用户初稿。
- 核心痛点。
- 核心功能假设。

### 3.4 示例

```text
产品：英语学习平台
定位：面向初中级英语学习者的语境听写与词汇记忆平台
核心痛点：背单词脱离语境，听力和拼写无法联动
核心功能：听一句英语音频，根据难度填空或整句听写
```

## 4. 阶段二：轻量调研

### 4.1 目标

确认产品方向是否有市场基础、竞品参考和可行技术路径。

### 4.2 调研内容

- 市场趋势。
- 竞品功能。
- 用户需求。
- 技术可行性。
- 商业化路径。

### 4.3 产出物

- 简要调研结论。
- 竞品功能参考。
- 市场机会。
- 风险点。

### 4.4 注意事项

- 不要陷入过度调研。
- 调研只服务于决策。
- 第一版重点看“是否值得做”，不是写行业报告。

## 5. 阶段三：产品方案

### 5.1 目标

形成产品需求文档 PRD，明确产品定位、用户、功能、路线图。

### 5.2 推荐文档

```text
docs/product-requirements.md
```

### 5.3 PRD 内容

- 产品概述。
- 产品定位。
- 目标用户。
- 核心价值。
- 支持端。
- 核心功能。
- 内容体系。
- 商业模式。
- 版本路线图。
- 待讨论问题。

### 5.4 判断标准

PRD 不需要一次写完，但必须能回答：

- 做什么？
- 给谁用？
- 为什么用户需要？
- 第一版先做什么？
- 后续可以扩展什么？

## 6. 阶段四：功能规格

### 6.1 目标

把产品想法拆成页面、流程、规则和验收标准。

### 6.2 推荐文档

```text
docs/functional-spec.md
```

### 6.3 内容结构

- 用户角色。
- 信息架构。
- 核心业务流程。
- 功能模块。
- 页面元素。
- 交互规则。
- 权限规则。
- 非功能要求。
- MVP 验收清单。

### 6.4 判断标准

开发人员看到功能规格后，应该知道：

- 页面上有什么。
- 用户怎么操作。
- 后端需要保存什么。
- 什么情况算正确。
- 什么功能暂时不做。

## 7. 阶段五：技术架构

### 7.1 目标

确认技术栈、系统边界、数据模型和部署方式。

### 7.2 推荐文档

```text
docs/technical-architecture.md
```

### 7.3 内容结构

- 技术目标。
- 总体架构。
- 技术选型。
- 应用划分。
- 后端模块。
- 核心领域模型。
- 数据库表建议。
- API 草案。
- 文件存储。
- AI / 第三方服务。
- 安全设计。
- 部署建议。
- 技术风险。

### 7.4 技术选型原则

个人开发者优先：

- 熟悉度。
- 可维护性。
- AI 辅助开发友好。
- 本地开发简单。
- 后续可扩展。

不要一开始追求：

- 微服务。
- 多端同时开发。
- 复杂 DevOps。
- 过度抽象。

## 8. 阶段六：开发计划

### 8.1 目标

确定哪些先做，哪些后做，避免功能膨胀。

### 8.2 推荐文档

```text
docs/development-plan.md
```

### 8.3 内容结构

- 开发原则。
- 阶段总览。
- P0 工程骨架。
- P1 MVP 核心功能。
- P2 学习闭环 / 业务闭环。
- P3 AI / 高级能力。
- P4 后台和内容生产。
- P5 多端扩展。
- P6 商业化。
- 优先级清单。
- 不建议第一版开发的功能。
- 里程碑。
- 风险与取舍。

### 8.4 判断标准

每个功能都应该有明确归属：

- 必须先做。
- MVP 后补齐。
- 验证后开发。
- 后续完善。
- 明确不做。

## 9. 阶段七：MVP 范围确认

### 9.1 目标

在正式开发前锁定第一版边界。

### 9.2 推荐文档

```text
docs/mvp-scope-and-prototype.md
```

### 9.3 内容结构

- MVP 核心验证问题。
- 第一版目标用户。
- 第一批内容方向。
- 必做功能。
- 暂不开发功能。
- 核心用户链路。
- 页面原型清单。
- 第一版数据模型范围。
- 产品验收标准。
- 技术验收标准。
- 内测验收标准。
- 开发前确认项。

### 9.4 MVP 判断标准

MVP 不是功能少，而是刚好能验证核心价值。

一个合格 MVP 应该：

- 能让用户完成完整核心流程。
- 能记录关键数据。
- 能暴露真实问题。
- 能支撑下一轮产品判断。

## 10. 阶段八：页面原型

### 10.1 目标

在写代码前确认页面结构和用户路径。

### 10.2 原型粒度

第一版只需要低保真原型：

- 页面有什么区域。
- 按钮在哪里。
- 用户点击后去哪。
- 成功和失败状态如何展示。

### 10.3 推荐先画页面

- 登录页。
- 引导页。
- 首页 / 工作台。
- 核心功能页。
- 结果反馈页。
- 列表页。
- 管理后台核心页面。

### 10.4 注意事项

- 不要一开始追求视觉精修。
- 先验证流程，再优化 UI。
- 页面原型应和 MVP 范围一致。

## 11. 阶段九：工程骨架

### 11.1 目标

让项目本地可运行，为后续功能开发打基础。

### 11.2 推荐目录

```text
apps/
  web/        # 前端
  api/        # 后端
infra/        # 本地基础设施
docs/         # 文档
scripts/      # 辅助脚本
```

### 11.3 必做事项

- 初始化前端项目。
- 初始化后端项目。
- 配置数据库。
- 配置文件存储。
- 配置环境变量。
- 配置 `.gitignore`。
- 添加 README 或启动说明。
- 跑通健康检查接口。
- 跑通 Swagger / API 文档。

### 11.4 本项目示例

```text
前端：Next.js + TypeScript + Tailwind CSS + shadcn/ui
后端：ASP.NET Core Web API + C#
数据库：PostgreSQL
文件存储：MinIO
```

### 11.5 验收标准

- 前端可以本地启动。
- 后端可以本地启动。
- 数据库可以连接。
- 文件存储可以连接。
- API 文档可以访问。
- `/health` 返回正常。

## 12. 阶段十：核心链路开发

### 12.1 目标

优先跑通产品最核心的一条业务链路。

### 12.2 开发顺序

1. 数据模型。
2. 基础接口。
3. 管理端录入。
4. 用户端展示。
5. 用户提交。
6. 后端处理。
7. 数据保存。
8. 结果反馈。

### 12.3 本项目核心链路

```text
管理员录入英文句子
↓
Piper TTS 生成音频
↓
音频上传 MinIO
↓
句子发布
↓
用户获取题目
↓
用户播放音频
↓
用户填空 / 听写
↓
后端判题
↓
保存答题记录
↓
错词进入错词本
```

### 12.4 注意事项

- 先打通一条链路，不要同时做所有功能。
- 可以先写死少量数据，再做完整后台。
- 核心链路能跑通后，再逐步补体验。

## 13. 阶段十一：内测验证

### 13.1 目标

用真实用户验证 MVP 是否有价值。

### 13.2 内测规模

建议第一轮：

- 5 到 10 人。
- 使用 3 到 7 天。
- 每天完成一轮核心任务。

### 13.3 观察指标

- 用户是否能独立完成流程。
- 用户是否理解功能。
- 用户是否愿意继续使用。
- 用户在哪一步卡住。
- 用户觉得最有价值的地方是什么。
- 用户是否愿意付费。

### 13.4 数据指标

- 注册转化率。
- 首次任务完成率。
- 次日留存。
- 平均练习题数。
- 错误率。
- 重复练习率。
- 反馈满意度。

## 14. 阶段十二：迭代与商业化

### 14.1 迭代顺序

根据内测反馈决定下一步，不要按想象堆功能。

常见顺序：

- 修复流程卡点。
- 补充内容。
- 优化页面体验。
- 增加复习机制。
- 增加高级功能。
- 接入支付。
- 扩展多端。

### 14.2 商业化前提

建议满足以下条件后再做完整商业化：

- 核心功能有人持续使用。
- 用户能明确说出价值。
- 有人愿意为高级能力付费。
- 内容生产流程可持续。

## 16. 每次新项目启动检查清单

### 产品

- 是否明确目标用户？
- 是否明确核心痛点？
- 是否明确第一版只验证什么？
- 是否明确哪些功能不做？

### 功能

- 是否有核心用户链路？
- 是否有页面清单？
- 是否有验收标准？
- 是否有后台管理范围？

### 技术

- 是否确认前端技术栈？
- 是否确认后端技术栈？
- 是否确认数据库？
- 是否确认文件存储？
- 是否确认第三方服务？
- 是否能本地启动？

### 开发

- 是否有工程目录？
- 是否有环境变量模板？
- 是否有本地基础设施？
- 是否有 Git 仓库？
- 是否有 README 或启动说明？

### 验证

- 是否准备内测用户？
- 是否准备初始内容？
- 是否定义成功指标？
- 是否准备收集反馈？

## 17. 推荐下一步动作

当以上文档完成后，不要继续无限写文档，应进入工程搭建：

1. 创建前端项目。
2. 创建后端项目。
3. 创建本地基础设施。
4. 跑通健康检查。
5. 跑通核心链路。
